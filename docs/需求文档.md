# 旅行手帐 · 需求文档

状态：草稿 v1 · 风格已定稿（M0 完成），本文档定义 M1 之后要做什么。

---

## 1. 这是什么

一个**手帐式的旅行记录本**。不是行程规划器，不是攻略社区，不是账本。
它要解决的是：一次旅行结束后，照片、票根、花了多少钱、去了哪几个地方，
散在相册和备忘录里，过两年就想不起来了 —— 把这些拼成一页能看的东西。

两个分区：

- **已旅行**：发生过的事。照片、逐日行程、花销、当时写的几句话。
- **待出行**：还没发生的事。订好的酒店、预算、想去的地方。

同一套数据模型、同一套版面，区别只在状态。待出行的卡片视觉上淡一档
（`.title.plan`），因为它还没成为回忆。

### 1.1 为什么值得做（求职视角）

这个项目要能在面试里讲 20 分钟，所以刻意留了三处有技术含量的地方：

1. **手绘渲染管线**：构建时用 fontTools 抽字形轮廓 → 运行时交给 rough.js 描边，
   标题的笔画本身在抖，不是把字当一块砖随机旋转。同一支笔画地图海岸线、
   插图、标题，风格自洽。
2. **确定性排版引擎**：拼贴要"看着随机"但必须"每次一样"（否则没法导出、没法测）。
   同一份数据 + 同一 seed → 像素级同一版面。
3. **录入 provider 抽象 + 评测集**：录入是这类产品的真正难点。用统一接口把
   "手工填表 / 粘贴一段文本 / 读照片 EXIF / 未来接 MCP" 做成可替换的
   provider，并且**有评测集能证明解析对不对**，而不是"我试了几条感觉还行"。

不打算讲的：CRUD、路由、响应式布局。那些是及格线。

## 2. 范围

### 做

- 单人使用，数据在本地（一个 JSON + 一个图片目录）
- Web 优先，能在手机浏览器上看
- 能导出：单文件 HTML（离线可开）、单页 PNG/PDF（当明信片发出去）
- 航线弧：**只从用户手输的起点/终点城市生成**

### 不做（明确划掉，避免自己往里加）

- **不碰邮箱**。不解析订单邮件、不接 IMAP、不要授权。航线只来自手输。
- 不做多人协作、评论、社交
- 不做实时机票/酒店比价
- 不做云端账号体系（起步阶段连后端都没有）
- 小程序：延后。先把 Web 做完，打包和合规是另一个话题。

## 3. 数据模型

分两层。**内核层不认识"旅行"这个词** —— 这样以后想做"读书手帐""搬家手帐"
不用重写引擎，也是这个项目值得讲的地方。

### 3.1 内核层

```
Entry  一条记录，手帐上的一个"贴片"
  id          string
  type        string        // 皮肤自己定义，内核只当字符串
  title       string
  time        {start, end?} // ISO；end 可空表示一个时刻
  place?      {name, city?, lat?, lon?}
  body?       string        // 手写体的一段话
  media       Media[]
  tags        string[]
  data        object        // 皮肤专属字段全塞这儿，内核不解释
  source      {provider, ref?, confidence}  // 谁录进来的、可信度
  layout?     {x, y, w, h, rot, z, pin}     // 手动覆写过的版面，pin=true 不再自动排

Media
  id, path, kind: photo|scan|drawing|image, w, h, exif?: {time, lat, lon}

Collection  一组 Entry，对应手帐的一"页"或一"本"
  id, title, status, time:{start,end}, entries: Entry[], seed: number
```

`seed` 是排版随机数的种子，存在数据里 —— 所以版面可复现，换 seed 就是"重新拼一次"。

`Media.path` 三种写法，`Kernel.mediaRef(path, images)` 是**唯一**判它是哪种的地方
（照片墙、封面相纸、看大图、明信片、编辑器缩略图五处都走它，加一类媒体只改一处）：

| 写法 | 是什么 | 怎么画 |
|---|---|---|
| `art:fuji` | 内置矢量场景插画（11 张，`sketch.js` 的 `ART` 库） | rough.js 当场描出 SVG，换笔换色能重绘 |
| `img:kyoto` | 位图场景插画（8 张，`media/*.jpg` 1000×700） | `<img>` 贴 data: URI；查不到名字**明说「缺图 xxx」，不换一张顶上**（§3.2 一律不猜） |
| 其它 | 普通图片地址 | 当 `src` 直接用 |

`img:` 的位图由 `build-data.py` 读成 data: URI **内联进 `data/bundle.js`**，不留
`media/kyoto.jpg` 这种相对路径 —— 单文件导出只内联 `<link>` 和 `<script src>`，
数据里的路径它扫不到（会照旧报「外部依赖 none」却裂图）；而明信片存 PNG / PDF 是把
SVG 塞进 `<img>`，那时候 SVG 成了独立文档，外部文件一律读不到。代价是 bundle
从 96KB 胖到 1.2MB，`index.standalone.html` 从 1.2MB 涨到 2.3MB。

**换图在页面上做，不用去改 JSON。** 编辑器里「📷 照片」一栏，每张一行：缩略图 +
说明 + 「换成」下拉（内置的 `art:` 矢量插画和 `img:` 位图都列出来）+ 「贴地址」输入框
（自己的图，三种写法都收）+ 「↑ 上移」+ 「删除」，另有「＋ 加一张」。三件事得咬住：

- **顺序就是上墙顺序**，第一张还兼当封面那张相纸，所以「上移」换的是 `entries` 里的
  真实位置，不是只换页面上的样子 —— 否则点开看大图的序号会错位。
- 只在这里改 `media[0].path`，**怎么画仍然是 `Kernel.mediaRef()` 一处说了算**。
- 填了个查不到的名字，当场写「缺图 xxx」并在下面给一行红字说怎么补，
  **不静默换一张顶上**（§3.2 一律不猜）。

### 3.2 旅行皮肤层

`Trip = Collection + data{ status, budget, currency, cities[], cover }`

状态机：`planned（待出行）→ ongoing（进行中）→ done（已旅行）`
按日期自动推进，允许手动锁定（比如行程取消了，停在 planned 并标记 cancelled）。

落地方式（M3 定下来）：**状态是算出来的，不是存出来的**。`TripView.statusOf(trip, now)`
拿 `time.start` / `time.end` 跟今天比 —— 没到出发日是 `planned`，在中间是 `ongoing`，
过了结束日是 `done`。数据里的 `status` 只是「用户手写的那一笔」，两种情况才轮到它说话：
`status === 'cancelled'`（取消了，停在原地）和 `data.lockStatus === true`（用户明确锁了）。
没填开始日期的按存的算，猜不出来不猜。
分栏（书架的三栏、`summary()` 的 done / plan）一律看算出来的状态，
所以去年出发的那趟不会今天还挂在「待出行」下面等人去改下拉框。
编辑器里的「状态」默认是「跟着日期走」，选具体某一档就是上锁；选回自动时顺手把
`status` 对齐成当下算出来的值，导出的 JSON 里不留旧状态。

Entry 的 type 取值与 `data` 字段：

| type    | 含义     | data 字段 |
|---------|----------|-----------|
| `leg`   | 交通段   | `from`, `to`（城市或 IATA）, `mode: air\|rail\|bus\|ferry\|car`, `code?`, `flown: bool` |
| `place` | 去了哪儿 | `day`（第几天）, `duration?`, `rating?` |
| `spend` | 花销     | `amount`, `currency`, `category: 交通\|住\|吃\|门票\|购物\|其他` |
| `stay`  | 住宿     | `checkIn`, `checkOut`, `booked: bool`, `price?` |
| `note`  | 写的话   | （无） |
| `photo` | 照片     | （无，内容在 media） |

**航线只看 `leg.from/to`**，`flown` 决定线型：已飞是实线 + 端点实心，
计划是虚线 + 端点空心。

城市 / 机场 → 坐标查**两层表**，`Store.places()` 合并，用户那层压在查表上面：

| 层 | 哪来的 | 存在哪 | 谁改得动 |
|---|---|---|---|
| `data.places` | `data/places.json`，现 253 条；key 可以是 IATA 码，也可以是中文地名 | 构建产物 `bundle.js`，只读 | 改仓库 + 重新构建 |
| `data.myPlaces` | 用户在页面上补的 | 本机 `localStorage` | 页面上随时改 |

**查不到就让用户补，一律不猜。** 查不到的码由 `derive()` 收进 `unknownCodes`
（地图那边是 `atlas().unknown`）：那几段航线**不画**，编辑器的「航段」和 `#/map` 都把名单列出来。
补坐标有两条路，都在编辑器里那一码一行的位置上：

1. **手填经纬度** —— 空框读成 `null` 而不是 0（0 是条真经线），两个都填齐才写回；
2. **去地图上点** —— 跳 `#/map/CODE` 进「点图补坐标」模式，点画布任意一处，
   反投影成经纬度存回来再退回编辑器。这一模式下点线 / 点城市不再跳走，那一下也是在选位置；
   地球视角下点到地球背面反投影给不出点，那次点击当没点。

越界的值（|经| > 180 / |纬| > 90）`Store.setPlace()` 直接不收，并当场提示。补进去的只落在
`myPlaces`，**不写回 `data/places.json`** —— 那是构建产物，浏览器里改不动它；
哪天查表里补上了同一个码，查表那份自然接管。`exportJSON()` 里 `myPlaces` 单独一段，
为空时不写，导出的形状跟仓库里那份一致。改起降码要重画**整个编辑器**，
否则「查不到坐标」这几行不会当场出现，破了 §4.8 的 100ms 反馈。

## 4. 功能需求

### 4.1 已旅行卡片（P0）

- 标题（手写渲染）、副标题、日期范围、城市 chip
- 照片墙：2~5 张，带手撕胶带装饰，可点开看大图
- 逐日行程：第 N 天 + 地点串，超过 5 天折叠
- 数字条：天数 / 城市数 / 照片数 / 总花销（按 `spend` 汇总，多币种按录入时汇率折算，汇率存进数据不实时查）
- 航段条：`SHA → HND` + 日期 + 交通方式图标
- 手写的一段话（`note`）

### 4.2 待出行卡片（P0）

- 同一套版式，标题淡一档（已实现）
- 倒计时：距出发 N 天
- 预算条：预算 vs 已支出（定金、机票已付的部分），进度用手绘线条画
- 已订 / 待订清单：`stay.booked` 和 `leg.flown=false` 生成
- 想去的地方：`place` 但没有 `day`
- 「想去的样子」照片墙：`photo` 那几条也上墙（M5 补）。参考图、别人拍的、上次去拍的 ——
  不是回忆，所以整排淡一档（`.photos.plan`），跟标题淡一档同一个道理。
  不另写一套版式，复用 §4.1 那个 `photoWall`，序号也还是 `wallPhotos()` 那一份，
  所以点开看大图跟已旅行走的是同一条路（`#/trip/:id/photo/:n`）。
- 出发日一到自动变「旅行中」（副标题换成「第 N 天 / 共 M 天」，书架上单独一栏
  `旅行中 · NOW`），结束日一过自动变「已旅行」换成 §4.1 那套版式 —— 见 §3.2 状态机。
  取消的那趟不倒计时，卡片上写「这趟取消了 · 想去了再改回来」。

### 4.3 地图（P0，原型已有）

- 摊平（等距圆柱，接缝在 20°W）/ 地球（正交投影，可拖拽旋转）两种视图
- 所有 `leg` 画成弧线，已飞/计划两种线型
- 城市点 + 名称标注，标注避让（同一区域挤在一起时只显示最高优先级）
- 拖动时降低海岸线精度保帧率（原型已实现 `tol` 粗化）

实现分工（M3 落地时定下来的）：`map.js` 只画，不知道"旅行"是什么；
航线一律由 `TripView.atlas()` 从真实 `leg` 算好后传进去 —— 图上每一段都对应
用户真填的一条航段，`data/places.json` 里查不到坐标的段不画、也不猜，
名单交给页面列出来提示补坐标。同名城市按名字去重（SHA / PVG 都算上海一座）。
避让做法：离已经写过名字的城市不到 52×26 px 就只画圈，名字留给 hover 的 `<title>`。

### 4.4 拼贴排版引擎（P1，本项目技术重点）

输入：`Entry[]` + 画布尺寸 + seed
输出：每个 Entry 的 `{x, y, w, h, rot, z}`

规则：

1. **网格基底**：先按内容重要度（照片 > 数字条 > 行程 > 花销 > note）分配格子，
   保证信息层级不乱。
2. **手抖偏移**：在格子内做 ±4px 平移、±2° 旋转、±3% 缩放，全部由 seed 决定。
3. **允许照片轻微重叠**（这是拼贴的灵魂），但**文字区域永不被遮挡** —— 硬约束。
4. **装饰自动落位**：胶带落在照片重叠处和卡片边缘，别针落在角上，不手工摆。
5. **手动覆写优先**：`entry.layout.pin = true` 的元素引擎不动。
6. **确定性**：同数据 + 同 seed → 同版面。这是导出和自动测试的前提。

### 4.5 手绘渲染（P0，已定稿，不再调）

- 线稿参数：手抖 1.2 / 弯曲 1.5 / 笔粗 0.8
- 标题参数：手抖 0.4 / 弯曲 0.4 / 笔粗 0.6 / 转角 0.3° / 上下 0.2px，霞鹜漫黑，实心填充
- 色块参数：抖动为墨线的 0.45 倍，错位 0.6px（否则细长矩形会被涂成一片叶子）
- 墨线支持 `w`（笔粗倍数）和 `s`（笔色）拉开层次；远景/纹理用淡墨
- 字库里没有轮廓的字自动退回普通文字渲染，加新文案不会缺字
- 换一支笔（reseed）：线稿和标题同时换，整页笔迹一致

### 4.6 录入 provider（P1，本项目第二个技术重点）

录入是这类产品真正的门槛。手工填 20 个字段没人愿意干，全自动又不可靠。
做法是把录入抽象成可替换的 provider，每个 provider 只干一件事：把某种输入变成 `Entry[]`。

```ts
interface Provider {
  id: string
  canHandle(input: unknown): boolean
  parse(input: unknown): Promise<Entry[]>   // 每个 Entry 自带 source.confidence
}
```

起步三个：

| provider | 输入 | 产出 | 备注 |
|----------|------|------|------|
| `manual`  | 表单 | 任意 type | confidence = 1，永远是兜底 |
| `text`    | 粘贴的一段话/行程 | `leg` `place` `spend` `stay` | 靠规则 + 词表，不联网 |
| `exif`    | 一批照片 | `photo` + 推断的 `place`/`day` | 读拍摄时间和 GPS，聚类成"第几天在哪儿" |

规则：

- **解析结果一律进"待确认"区**，用户点确认才落库。低 confidence 的字段高亮。
- provider 不允许写除自己产出之外的字段，避免相互覆盖。
- **不做邮箱 provider**（见范围）。未来可以加 `mcp` provider，从个人上下文服务里取，但那是另一个项目。

### 4.7 导出（P1）

- **单文件 HTML**：css/js/字体/数据/图片全部内联，`file://` 双击能开，能发给别人
- **明信片是导出的单位，不是"把详情页截下来"**：详情页按 app 做、竖着自由滚，没有"一页"
  可言，也就没法算留白率、没法发出去。所以 `#/trip/:id/card` 是另一层 ——
  900×1200 的固定画布，版面全交给 §4.4 的排版引擎算
- **三种格式，一条底线**（`bake.js`，不引第三方库）：

  | 格式 | 怎么出来的 | 依赖 |
  |------|-----------|------|
  | SVG | 序列化那棵 SVG，@font-face 留外链 | 无 —— 兜底就是它 |
  | PNG | SVG 塞进 `<img>` → canvas → `toDataURL` | canvas + Blob |
  | PDF | 同上取 JPEG，手拼一个 PDF 1.4：一页 + 一张 `/DCTDecode` | canvas + Blob |

  底线是**导不出来就说导不出来**：缺 canvas / 缺 Blob / 读不到字体，都把原因写在页面上，
  不静默失败也不假装成功。PDF 页面尺寸按 SVG 单位的一半算点数（900×1200 → 450×600pt，
  6.25×8.33 英寸），配 2 倍栅格约 288dpi；调栅格倍数只改清晰度，不改纸的大小。
- 一旦 SVG 被塞进 `<img>` 就成了独立文档，页面上外链的 `fonts/inline.css` 不跟着走，
  所以 PNG / PDF 要把 `@font-face` 抄进 SVG 自己的 `<style>`。`file://` 下浏览器不让读
  跨源样式表的 `cssRules`（每个本地文件都是独立来源），那时候正文会换一支字 —— 页面上说明白，
  从 http 打开就正常
- 导出必须依赖排版引擎的确定性：同一份数据导两次，结果一致

### 4.8 页面结构与导航（P0）

**手帐是视觉隐喻，交互按 app 做。** 这两句都要成立，所以先划清界限：
纸、墨、胶带、翻页转场负责"像手帐"；导航、滚动、手势、状态记忆负责"像 app"。
**不许做成 PPT** —— 一屏一页、只有上一页下一页、内容为了塞进一屏被截断，都是跑偏。

**导航是一个栈，不是一串幻灯片。**

```
cover    #/                   封面：贴满东西的书皮，点「翻开 →」（结构见下）
shelf    #/shelf              书架：扉页说明 + 竖向手绘时间轴，旅行中在最上、已旅行居中、待出行在下，长则滚动
trip     #/trip/014           某一趟：从书架上那张卡片原位展开，页内自由滚动
edit     #/trip/014/edit      填数字：同一层的另一种形态，不是新开一页
photo    #/trip/014/photo/3   照片大图：左右滑切换，下拉关掉，背景是上一层
card     #/trip/014/card      这一趟的明信片：固定一张纸，可存 PNG / PDF / SVG（§4.7）
map      #/map                §4.3 的地图，所有 leg
map:pick #/map/HKG            「点图补坐标」模式：给某个查不到的码点一个位置（§3.2）
stats    #/stats              足迹总览：几趟 / 几天 / 几座城市 / 多少公里 / 花了多少
about    #/about              这本手帐怎么做的（面试用，讲技术不讲行程）
debug    #/debug              等于 #/shelf，另外把调参条放出来
```

- **hash 路由，不用 history API**：`file://` 下 `pushState` 直接抛异常，单文件导出后链接还得能点。
- 后退（浏览器按钮 / 右滑手势 / `Esc`）= 出栈，回到**来处**，不是机械的"上一页"。
  从地图点进某趟，退回去是地图；从书架点进去，退回去是书架。
  看大图时左右键和左右滑改成翻页（这一层没有"上一趟"可去），`Esc` 关掉。
- 书架、地图、足迹是并列入口，不是书的第 2、第 8 页 —— 宽屏放在侧边书脊上，窄屏放底部 tab。
- 足迹总览上的每个数字都由 `TripView.summary()` 现算：改一笔花销、加一段航线，
  这一页立刻跟着变。页面自己不许再算一遍（数字对不上都是这么来的）。

**封面是一张贴满东西的书皮，不是启动页。** 只有书名和一枚邮戳的话，它就是一张「点一下才进得去」的
过场页 —— 那是 PPT 味。所以封面自己就得有内容可看，一眼能看出这本子记了多少东西：

| 贴在上面的 | 出处 |
|---|---|
| 两条 washi 胶带（左上 −5°、右下 +3.5°，压出纸边）+ 右上角邮票 | 装饰，`data-tape` / `data-art` |
| 手写书名「旅行手帐」+ 一行 `TRAVEL NOTEBOOK · 手绘` | 写死的书名（不在 `trips.json` 里，所以补在 `build-handtype.py` 的 `EXTRA`） |
| 年份跨度（`2023 – 2025`，只有一年就写一年） | `summary().byYear`，日期没填的记成「未知」，跳过 |
| 一张相纸（带胶带的照片） | **最近一趟真填的第一张照片**，三种写法都走 `T.mediaNode()`（§3.1）。换数据就换图，不是挑一张好看的写死 |
| 一行城市名（前 4 座，多了缀「等 N 座」） | `summary().atlas.cities`，只算走过的 |
| 四个数字：趟 / 天 / 公里 / 座城市 | `summary()`，同 `#/stats` 一个函数 |
| 「翻开 →」按钮 | 唯一的出口，去 `#/shelf` |
| 三枚贴纸（`plane` / `camera` / `ticket`，各歪一点） | 手贴上去的不会齐 |
| 一句现在的话 | 三档：「下一趟 · X，还有 N 天」／「还有 N 趟在计划里」／「本子还是空的 —— 翻开，记第一趟」 |

两条硬规矩：

- **每个数字都出自 `TripView.summary()`**，跟足迹总览同一个来源。封面自己算一遍必然对不上
  （§3.1 页面不许再算一遍）。所以「清空」示例数据之后，封面立刻变成一本空本子 —— 没有一处是写死的。
- **手绘框只有最外面 `.book` 这一个**（版面规整优先）。里面的层次靠胶带、相纸、贴纸和一条细线拉开，
  不往里套第二层抖动的方框。

**「这本子怎么用」是书架顶上的一张扉页贴纸，不是封面和书架之间的一页。** 夹一页说明进去就等于加了
一张可跳过的启动页。它默认展开，点「折起 ×」收掉并记在 `localStorage`，右上角的 `?` 能叫回来。
书架**底部**另有「载入示例 · 另 N 趟」和「清空」：首屏只装 2 趟已旅行 + 2 趟待出行
（`data/trips.json`），剩下 10 趟搁在 `data/samples.json`，跟着 bundle 一起发，
所以离线单文件里也点得动。「清空」和 `#/about` 的「恢复示例数据」是两件事 ——
后者是撤回本机改动回到出厂那 4 趟，前者是一趟都不留、从空本子开始记。
出厂那 4 趟里三趟带位图插画（`img:`），**最近一趟已旅行也带** —— 一进来封面那张相纸
就是位图，不用先点「载入示例」才看得见（`test-page.js` 有一条断言把这个锁住）。

**「出厂那几趟更新了」：本机存着旧的一份时，书架顶上得说一句。** 来过一次就会往
`localStorage` 存一份，而 `Store.load()` 里本机那份 `trips` 优先 —— 从那以后打开
永远是那一份，仓库里新加的行程、换的插画他一辈子看不到，**页面上还一点迹象都没有**
（「刷新了怎么没差别」就是这么来的）。这不是 bug 是设计（本机改动优先），但得让人知道。
做法：`build-data.py` 给出厂数据算一枚**内容哈希指纹**（`stamp`，只算 `trips` +
`samples`），`Store` 把「存这份时看到的是哪一版」一起存下来，对不上就 `stale()`。
书架顶上那张卡给两个出口，都是一下点完：「取新的 · 丢掉本机改动」（`reset()`，先确认）
和「不用了 · 留着我的」（记下现在这一版，下次不再问，数据一字不改）。两条边界：

- **指纹不能用构建时间** —— 那样每跑一遍构建、内容一个字没改，回头客都会被问一次，
  问多了就没人看了。也不把 `places` / `images` 算进来：那两样改了不影响「书架上是哪几趟」。
- **不自动覆盖**。存着的那份可能是人家自己记的东西。老版本没存指纹的当「不知道」，
  按过期处理 —— 宁可多问一次，也别让人对着半年前的书架以为这就是全部。

**反 PPT 的四条硬约束**（写代码时拿这四条自查）：

1. **内容不许为了"一屏装下"被裁**。详情页该多长就多长，竖向滚动；折叠只用于次要信息（§4.1 的逐日行程）。
2. **点击 100ms 内必须有反馈**。按下即变形（纸被按住的手感），不等转场算完。
3. **转场用共享元素**：书架上那张卡片放大成详情页，标题和封面图连续位移，不是整屏切换。
   翻书那套 3D `rotateY` 只留给封面 → 书架这一次，作为"翻开本子"的仪式感，别处不用。
4. **返回必须还原现场**：书架滚动位置、展开/折叠状态、看到第几张照片，退回去都在原样。

**动画只是转场，不许约束页内排版。** 约 300ms，CSS transform 实现，不引第三方翻书库
（turn.js 之类要 jQuery，还会把 DOM 结构绑死，跟单文件导出和排版确定性都打架）。
页内怎么摆照片、怎么塞手写块，仍然全权交给 M4 排版引擎 —— 一旦转场开始要求
"页内元素必须长成某种结构"，就说明写歪了。`prefers-reduced-motion` 时全部退化成直接切换。

**响应式：断点决定"一屏显示几层"，不改导航模型。**

| | 宽屏（≥ 900px） | 手机 |
|---|---|---|
| 书架 | 左侧常驻，详情在右侧展开 | 全屏一列，点进详情覆盖上来 |
| 入口 | 侧边书脊（书架 / 地图 / 关于） | 底部 tab |
| 返回 | 左上角箭头 + `Esc` | 右滑手势 + 箭头 |
| 照片大图 | 居中灯箱，方向键切换 | 全屏，左右滑切换，下拉关掉 |

同一份 `routes` 表、同一份数据、同一套卡片组件，只有"一屏显示几层"和手势不同。
手机优先：先把窄屏做对，宽屏是"多显示一列"。

**其它**

- 调参条（手抖 / 弯曲 / 笔粗那些滑块）默认藏起来，`#debug` 或按 `d` 唤出。
  那是我调风格用的，作品集第一眼不该看到滑块。
- 文件落位：`prototype/index.html` 是手帐本本体；`hand-drawn.html` 降级成风格样张页
  （贴纸墙、调参对比留在那儿自己看）；地图已并进 `#/map`（`map.js`），`map.html`
  留着当调笔的样张，自带国界 / 简化两个滑块和一份写死的示例航线，外观改 `map.js`。
- GitHub Pages 从仓库根发布，根目录放一个 `index.html` 重定向到 `prototype/index.html`，
  简历上放的就是这个链接。

## 5. 非功能需求

- **无后端**：起步阶段只有静态文件。数据是本地一个 `trips.json` + `media/` 目录
- **离线可用**：`file://` 双击能开。字体 base64 内联，数据内联，不发任何请求
- **性能预算**：首屏 < 1.5s；单页 SVG 节点 < 3000；拖地球重绘 < 150ms/帧
- **隐私**：没有任何数据离开这台机器。照片不上传，不做人脸识别
- **可访问性**：插图带 `aria-label`；手绘标题保留原文在 `data-hand-raw`，选中/朗读/搜索都拿得到文字

## 6. 技术选型与取舍

现在：**原生 HTML/CSS/JS + rough.js + d3-geo + topojson**，无框架、无打包器。

理由：这个项目的价值在渲染和排版，不在组件化。而且"单文件导出"这个需求
跟框架的构建产物天然冲突，越简单越好打包。

什么时候重新评估：M4 排版可拖拽编辑之后，手写 DOM diff 会开始难受。
届时倾向 Svelte 或 Web Components —— 都能编译成不需要运行时的单文件。

不用 Canvas 而用 SVG：因为要导出、要可选中文字、要 CSS 换色，而且节点数在预算内。

### 6.1 跨端约束（为 M7 小程序留门）

小程序没有 DOM 和 SVG，但**手绘算法本身跟渲染器无关**：`rough.generator()`
只吐 `move` / `lineTo` / `bcurveTo` 三种指令，数据是裸数字，喂给
`<canvas type="2d">` 就是两三百行的第二个后端。同 seed 出同一组指令，两端笔迹一致。

所以现在唯一要守的规矩：**SVG 调用不许漏进插图库和排版引擎**。中间隔一层：

```js
draw.path(d, {fill, stroke, w, dash})   // 后端可以是 svg，也可以是 canvas
draw.circle(cx, cy, r, style)
draw.group(transform, fn)
```

`ART` 解释器、`handtype`、排版引擎只认这个接口，不碰 `rc.path()` 和 `setAttribute`。

M4 抽出来了：`draw.js` → `window.Draw`，笔（`S`）、颜料（`C`）、所有 `rough` 调用都关在里面。
`sketch.js` 的 `ART` 解释器、`postcard.js` 都只走它。验收方式是**改完这一层，
渲染结果字节不变**（`node test-page.js` 里那条"两次渲染必须一致"的快照就是这条的守卫）。
`map.js` 还在直接用 `rc.*` —— 它是最后一个耦合点，等真要做 canvas 后端时再动。

按这条规矩，跨端时的成本分布：

- 白拿：数据模型、状态机、汇总、排版引擎、`ART` 图元、字形轮廓、d3-geo
- 重写：渲染后端（canvas 2d）、卡片版式（WXML/WXSS）
- 丢掉：单文件 HTML 导出、PDF、CSS 换色
- 反而变好：导出 PNG 存相册、分享到会话

不用 Taro / uni-app：它转的是组件和路由，帮不上渲染器的忙，还会塞进一套构建流程，
跟单文件导出冲突。也不指望 `<web-view>` 套 Web 版 —— 个人主体小程序用不了
（政策会变，真要走之前查一遍开发者文档）。

## 7. 评测集（这是本项目和"作品集玩具"的区别）

### 7.1 解析评测

- 20~30 条真实风格的粘贴文本（订单确认、行程截图 OCR、自己随手记的一段话）
- 每条人工标注期望的 `Entry[]`
- 指标：字段级 precision / recall / F1。**漏解析比错解析可接受**（漏了用户会补，错了用户不一定发现）
- 回归门槛：改解析规则后 F1 不许降

### 7.2 排版评测

- 10 份数据 × 固定 seed → 快照断言：
  - 文字遮挡数 = 0（硬约束）
  - 元素出画布数 = 0
  - 照片重叠率落在 5%~20% 区间（太少呆板，太多糊）
  - 留白率落在 15%~35%
- 另有一份人工评分表（拥挤感 / 层级清晰 / 像不像手帐），每个里程碑打一次

现状（M4）：`Layout.audit()` 现算这四个数，出厂那 4 趟每趟都过一遍
（`node prototype/test-page.js --pc` 打出逐趟的表；点「载入示例」补齐 14 趟后同样能过）。
压字和出界是硬 0 ——
**靠结构保证，不是排完再检查**：照片只在自己那几行里互相挤，文字块单独占行。
留白落在 19%~27%。重叠率只在**照片 ≥ 2 张**时才有意义（2~3 张的那两趟是 7.4% / 9.5%），
没有照片的趟数是 0% —— 没有第二张可压，这一条就不适用，测试也只对多图的趟数断言。
明信片页上那行审计数字（`#debug` 才显示）念的就是同一个 `audit()`，不另算一遍。

### 7.3 渲染回归

把现有的「stub DOM 跑页面 → 序列化 SVG → cairosvg 转 PNG」这条链固化成测试，
改插图或改参数后先看图，元素数对不出风格问题。

现状（`node prototype/test-page.js`，257 条断言）：两页都跑。`hand-drawn.html` 查
卡片数 / 插图 / 描边 / 折算出来的数字 / 折叠，外加「同 seed 两次渲染完全一致」；
`index.html` 走一遍导航（封面 → 书架 → 详情 → 编辑 → 地图 / 足迹 / 照片大图 / 关于），
并且**真的去点、真的去填**：填一个预算就断言仓库和卡片上的数字都跟着变，
点「加一笔」断言 entry 多一条，点照片墙第二张断言开到 `photo/1`。
状态机也在这里锁：`statusOf()` 五种输入（过去 / 未来 / 跨今天 / 锁定 / 取消）各断一次，
再在编辑器里**只改日期不碰状态框** —— 改到过去卡片得换成数字条那套、改成跨今天
书架上得冒出「旅行中 · NOW」这一栏、锁回待出行得停住，最后把日期放回去。
跨页一致性也在这里锁：地图上的航线行数必须等于 `atlas()` 算出来的段数，
足迹页的条数必须等于年份 + 类目数，照片墙张数必须等于 `wallPhotos()` 的长度 ——
三处对不上就说明有一层自己偷偷算了一遍。
案例页 `#/about` 同样被咬住：它上面那六个大号数字（趟数 / 记录数 / 航线段数 / 城市数 /
字形数 / 坐标表条数）必须跟仓库和 `atlas()` 现算的一致 —— 一页专门讲「数字只有一处出处」的页面，
自己抄一份就说不过去了。顺带这条断言还盯着 `handtype.js` 得在 `app.js` 之前加载
（否则直接开 `#/about` 时字形数是 0）。
stub DOM 不解析 HTML 静态标签，所以挂载点要在 `makeDocument()` 里手工登记；
`setTimeout` 在 stub 里同步执行，否则地图那种「等排版好了再画一帧」永远画不出来。

M4 做出来的是**明信片这一层**：`layout.js`（纯几何，不认识「旅行」）算版面，
`postcard.js` 把 `derive()` 的数字拆成贴片，`bake.js` 把画好的 SVG 存成 SVG / PNG / PDF，
入口是详情页底下的「做张明信片 →」，落在 `#/trip/:id/card`。
两处的做法值得记下来：**「文字不被遮挡」是结构保证，不是事后检查** —— 照片只在自己那几行里
互相挤，文字块单独占行，所以 `audit().textHits` 天生是 0，而不是排完再挪；
**胶带贴在 `spread()` 真压上的那条缝上**，不是「所有相交的照片对」—— 后者会把 2×2 的对角
也算进去，四张照片贴出六条胶带，其中两条压在谁身上都说不清。
顺手把 §6.1 的 `draw.js` 抽了（验收标准是渲染结果字节不变）。
留着没做的两件：**书架卡片 → 详情页的共享元素转场**（还是淡入 + 位移）和 `map.js`
仍直接调 `rc.*`。测试从 119 条涨到 206 条，多出来的是 §7.2 四条硬指标、同 seed 两次
排版一致、以及手拼 PDF 的 xref 字节偏移逐条验回去（假 JPEG 里特意塞了 >127 的字节，
哪天有人把偏移改成按字符数算就会被咬住）。

M6 先做了两件能立刻拿去面试的：**README** 和**案例页 `#/about`**。案例页讲技术不讲行程 ——
一句话说清「无框架 / 无后端 / 双击能开」、三处技术含量（手绘管线、确定性渲染、内核不认识「旅行」）、
四行「哪一页的数字从哪儿来」，最后是 `file://` 逼出来的那几个选择。上面的数字全部现算，
并且被 §7.3 的断言咬住。顺手补的两处：`build-fonts.py` 的 `SOURCES` 漏了 `map.js`
（地图图例那几句中文没进得意黑子集，会掉回系统字体），根目录补 `LICENSE`（代码 MIT，
字体按各自 OFL），得意黑的 OFL 正文放进 `prototype/fonts/`。
剩下的打磨是截图和导出的 PNG 明信片 —— M4 的导出已经做完，现在缺的只是找一台
有浏览器的机器点一下「存 PNG」，把图放进 README。

M6 第二批做的是**第一眼**（作品集第一屏的说服力）：示例数据瘦到出厂 4 趟
（2 走过 + 2 待出行，其余几趟挪进 `data/samples.json`，书架底部自取）、书架顶上加一张
可折起的扉页说明贴纸、手绘场景插画从 3 张扩到 11 张（另有 9 枚贴纸 / 图标）、
`data/places.json` 从 33 条扩到 253 条、
坐标查不到时可手填经纬度或去 `#/map/CODE` 点图补（§3.2 两层表）、封面从「书名 + 邮戳」
改成一张贴满东西的书皮（§4.8）。断言从 206 涨到 226 条，多出来的主要咬两件事：
封面上每个数字都必须等于 `summary()` 的对应字段，以及书架 strip 上不许再出现 chip 框
（`.strip .chip` 断言为空，防止版面又花回去）。

M6 第三批开了**位图场景插画这一类媒体**（§3.1 的 `img:`）：8 张 1000×700 的生成图进
`prototype/media/`，构建时内联成 data: URI。这本来是 §9 里「插画 LoRA 兜底」那条提前落地 ——
差别只在图现在是现成的、以后可以是模型出的，通道是同一个。做法上守住两条：
**判「这条 media 该怎么画」只在 `Kernel.mediaRef()` 一处**（照片墙、封面相纸、看大图、
明信片都改成走 `TripView.mediaNode()`，加一类媒体不用改四个地方），
**查不到名字就写「缺图 xxx」**、不退回随便一张插画（跟 §3.2 坐标查不到同一条规矩）。
顺手把香港那趟从 `art:street` 换成自己的图（原来跟东京共用一张插画），
并给伊斯坦布尔 / 开普敦 / 洛杉矶补了 3 趟示例（samples 7 → 10 趟）—— 洛杉矶的日期
故意排成最新那趟「已旅行」，所以点过「载入示例」之后封面那张相纸会换成位图。
断言 226 → 230 条：新的四条把每个 `art:` / `img:` 名字对着各自的表查一遍
（出厂 4 趟 + 示例 10 趟一起查），并要求 `img:` 解析出来必须是 data: URI ——
留成 `media/kyoto.jpg` 这种相对路径的话，单文件导出会照旧报「外部依赖 none」却裂图。

M6 第四批全是从一句反馈来的：**「在哪里看照片啊，我感觉刷新了没啥差别」**。
一句话里其实是三个独立的毛病，一个个堵掉（断言 230 → 257 条）：

- **一进来看不到位图**。位图全挂在待出行那两趟上，而待出行卡片当时没有照片墙 ——
  所以新用户一张位图都看不见，封面那张相纸也还是矢量插画。两头改：待出行补上
  「想去的样子」（§4.2），出厂四趟里换一趟带位图的已旅行进来（巴黎·伦敦 ⇄ 伊斯坦布尔，
  entry 74 → 64 条，samples 145 → 155 条），并加一条断言锁住「出厂封面那张必须是位图」。
- **图没法在页面上换**，只能去改 JSON —— 编辑器补「📷 照片」一栏（§3.1）。
- **刷新了没差别**，因为本机 `localStorage` 那份把出厂数据盖住了 —— 出厂数据加内容
  哈希指纹，对不上就在书架顶上说一句，给「取新的」/「留着我的」两个出口（§4.8）。

顺带把 `hand-drawn.html` 挑样张的规则从「最近那趟」改成「条目最多的那趟」：那一页是
给人看笔迹的，摊上条目最少的一趟就把照片墙、逐日行程折叠这些元素都摆不出来 ——
换数据时不该顺带把样张页画秃了。数字仍然是 `derive()` 现算，那里只决定画谁。
